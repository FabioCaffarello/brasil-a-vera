## Achados-chave

### Linguagem visual extraída do designer parceiro

Protótipo de referência (`usernamette/vera-politica`) trouxe paleta OKLCH dark-first calibrada. Em vez de copiar componentes em stack incompatível (TanStack Start + Vite + chamadas client-side à API da Câmara + mock auth), **extraímos os tokens e reconstruímos sobre nossa stack** (Next.js 16 + RSC + Drizzle + Neon + Cloudflare Workers).

Re-validação WCAG via `culori` exigiu **5 ajustes** sobre os valores originais do designer:

| Token (dark) | Designer | Nosso | Razão |
|---|---|---|---|
| `--foreground-muted` | `0.66` | `0.72` | Passa AAA em ambos surface e background |
| `--foreground-subtle` | (não tinha) | `0.63` | Novo token |
| `--destructive` | `0.66` | `0.55` | Designer dava 3.35 contra fg branco (FAIL AA); escurecido passa 5.22 |
| `--primary-foreground` | `0.99` (branco) | `0.14` = `--background` | Designer dava 3.21 sobre `--primary`; dark fg em bright primary é estratégia idêntica a success/warning do próprio designer |
| `--border` / `--border-strong` | alpha 8%/15% | lightness `0.3`/`0.4` | Decorativos (fora WCAG 1.4.11), mais visíveis no dark |

**30 pares funcionais** (15 dark + 15 light) passam WCAG AA. Tabela literal em `docs/architecture/WCAG-AUDIT.md`.

## Decisões registradas

### `bg-brand` em vez de `bg-primary` para token semântico

A paleta institucional já ocupa `--color-primary-50..950` (HEX, Variante 2 azul-marinho, Sprint 3.1). Reusar `--color-primary` para o novo token semântico criaria confusão entre "primary HEX shade" e "primary OKLCH semântico". `--color-brand` mantém os dois sistemas legíveis. Documentado em `DESIGN-TOKENS.md` desde PR #139.

### `--color-secondary`/`--color-accent`/`--color-input` NÃO introduzidos agora

Princípio leve do ADR-021 §4: não preemptar tokens sem consumer concreto. Mapeamos para tokens existentes (`surface-elevated`, `foreground`, `border-border-strong`) — semântica suficiente para as 10 primitivas Tier 1. Quando uma feature exigir diferenciação real (input dedicado em form de alerta na Wave 4.5, por exemplo), introduzimos com WCAG re-audit no PR daquela feature.

### `next-themes` removido (D4 do plano)

Sonner CLI instalou `next-themes` automaticamente — desinstalado em seguida via `npm uninstall next-themes`. Sprint 4.0 é dark only; toggle dark/light entra na Sprint 4.1. Sonner usa `theme="dark"` hardcoded até lá. Atualização concentrada nesta primitiva quando o toggle vier.

### `tw-animate-css` NÃO instalado (decisão diferida)

Dialog e Tabs do shadcn shipam com classes `data-[state=open]:animate-in`, `fade-out-0`, `zoom-in-95` etc. que requerem `tw-animate-css` plugin. **Não instalamos** — Radix gerencia mount/unmount instantâneo, dialog/tabs funcionam sem animação. Classes ficam no JSX para forward-compat: quando `tw-animate-css` for adicionado (decisão diferida para Sprint 4.1 ou 4.3 com base em uso real), animações ativam automaticamente sem editar primitivas.

### `/dev/design` é static (○), não dynamic

Conteúdo todo declarativo (sem queries de DB). Build-time render → zero custo serverless por visita. Cloudflare Workers serve do static asset diretamente. Próximo passo natural seria adicionar `data-theme="dark"` em vez de `.dark` class quando o shell global for refeito na 4.1.

### Wave renumeração formalizada

Em 2026-05-15 a Wave 4 (originalmente "Open Ground") passou a ser **"Design System & Frontend de Excelência"** com 6 sprints. O backlog open ground original migrou para **Wave 5 — Open Ground**. Sprints 3.3 (TSE, API REST) e 3.4 (Coerência, Grafo) marcadas como ⏸️ pausadas pendentes reavaliação ao final da Wave 4. Nota histórica permanente no topo do `ROADMAP.md`.
