## Resumo executivo

Tag final da Wave 4. Consolida 4 sprints (4.1, 4.2, 4.4, 4.6) sem tag
intermediária + reutiliza o conteúdo já tagueado em 4.3.

OKLCH (success, brand, warning, destructive, foreground, surface,
border, ring). Zero className em zinc/primary HEX legacy. Pirâmide de
confiança L1→L4 unificada visualmente em todo o produto.

análise ADR-019 — sem demanda observada justificando construção
especulativa. Infraestrutura de auth (Clerk + Workers Paid + middleware
expandido) já está pronta, dormente, para reativação quando aparecer
sinal real de uso. Tracking: [issue #174](https://github.com/FabioCaffarello/brasil-a-vera/issues/174).

**Critérios de performance (Sprint 4.3 D7)** ficam como **carryover
empírico**: plano de medição Lighthouse mobile entregue
([`LIGHTHOUSE-PLAN.md`](../architecture/LIGHTHOUSE-PLAN.md)) +
template de resultados ([`LIGHTHOUSE-RESULTS.md`](../architecture/LIGHTHOUSE-RESULTS.md))
para owner executar em ambiente production-like real. Princípio 13 —
sem medição = sem claim.

## Achados-chave (Wave inteira)

### Pirâmide de confiança unificada cross-rota

A pirâmide L1→L4 ficou visualmente coerente em todo o produto após
Sprint 4.6 PR 1. \`getTrustLevelColor\` centralizado em \`lib/trust.ts\`:

- L1 (oficial inteiro) → \`bg-success/10 text-success border-success/40\`
- L2 (agregação determinística) → \`bg-brand/10 text-brand border-brand/40\`
- L3 (cálculo derivado) → \`bg-warning/10 text-warning border-warning/40\`
- L4 (estimativa) → \`bg-warning/20 text-warning border-warning\`

Decisão deliberada: L4 NÃO usa destructive (que invoca alarme) — fica
em warning com saturação mais alta. L4 ainda é dado útil, apenas o
menos confiável; sinaliza "leia com mais atenção".

TrustBadge é consumido em ~10 detail pages + 2 análises L2 (Top 5
Afinidade, Pares Contraditórios) + `/docs/piramide-de-confianca` (onde
os 4 níveis aparecem lado a lado, fazendo a documentação visual e
textual contarem a mesma história).

### Escala de cor para % unificada em 4 rotas

Mesma escala `success ≥80 / foreground ≥50 / warning <50` em:

1. Alinhamento individual à bancada (perfil parlamentar)
2. Top 5 afinidade (perfil parlamentar)
3. Fidelidade interna média (perfil partido)
4. Concordância entre pares (comparar)

Cidadão lê a mesma faixa visual em qualquer % de fidelidade/alinhamento.

### Padrão "amber → warning subtle" para alertas guiados

`border-warning/40 bg-warning/X text-warning` aparece em 4 contextos
de "atenção redobrada" (não destructive, não alarme):

- `ParesContraditorios` caixas dos pares (Sprint 4.3 D4)
- `AlinhamentoBancada` box "amostra insuficiente"
- `ErrorState` /comparar — UUIDs inválidos
- /o-meu-parlamentar — "município não consta"

Erros guiados ganham warning; alarme reservado para destructive.

### TIPO_VOTO centralizado em `lib/format.ts`

`getTipoVotoStyle` mapeia SIM/NÃO/Abstenção/Ausente/Obstrução para
tokens semânticos. Consumido por 3 lugares:
- `votacao/votos-individuais`
- `parlamentar/votos-recentes`
- `parlamentar/pares-contraditorios`

Mudança em um arquivo único propaga consistência cross-rota.

### "Meu parlamentar" como brand-distinct

Navbar tem 5 links. 4 deles (Parlamentares, Proposições, Votações, Docs)
usam `text-foreground` (neutro). "Meu parlamentar" mantém `text-brand`
— é a porta de entrada cívica recomendada do site (Sprint 3.1 narrativa).

Decisão preservada na Sprint 4.6 PR 1.

### Bundle gzipped reduzido em ~20 KB

Adoção de primitivas Input + Button no SearchForm (Sprint 4.4 PR 3)
removeu classes \`primary-700/800\` inline que duplicavam o Button já
bundled.

| Estado | Bundle handler.mjs gzipped |

| Pós-Workers Paid (Sprint 4.2) | ~2.21 MB |
| Pós-Wave 4 (v0.4-final-public) | ~2.19 MB |

## Decisões registradas durante a Wave

### Sprint 4.5 deliberadamente pulada

Em 2026-05-16 (início Sprint 4.5), análise ADR-019 mostrou:

- Workers Paid contratado (Sprint 4.2) ✅
- Middleware Clerk expandido ✅
- `auth.protect()` dormente, pronto ✅
- **Sem demanda observada** de usuários para features autenticadas

Construir tabela `usuario_acompanhamento` + ADR LGPD-aware + 3 rotas
privadas sem trigger real seria especulativo. Decisão D0(a) da Sprint
4.6: pular 4.5, fazer 4.6, encerrar Wave 4.

Issue [#174](https://github.com/FabioCaffarello/brasil-a-vera/issues/174)
documenta pré-requisitos para reativação.

### Sprint 4.6 — escopo expandido honestamente

Início da Sprint 4.6 revelou que 12 arquivos ainda tinham zinc/primary
HEX (descoberta pré-sprint não-prevista no plano da Wave 4 original):

- Componentes universais: TrustBadge + Navbar
- /docs/* (5 páginas + 2 components compartilhados)
- /o-meu-parlamentar + 2 form components
- /feed

Plano original da 4.6 era apenas Lighthouse + polish. Decisão D0(a):
incorporar o reskin restante à 4.6 e fechar tudo em uma tag única.

Sweep final pós-PR 3 confirma: nenhum className renderizado usa
zinc/primary HEX. 4 arquivos ainda têm matches em comentários JSDoc
históricos (footer, layout, parlamentar-card, dev/layout) — sem churn.

### Lighthouse mobile diferido (princípio 13)

Critérios da Sprint 4.3 (LCP ≤ 2.5s, perf ≥ 95, a11y = 100) **não foram
medidos** localmente. Sprint 4.6 PR 4 entrega:

- \`LIGHTHOUSE-PLAN.md\` — procedimento completo (13 rotas, 4G throttling,
  3 runs por rota, 4 hipóteses de mitigação se LCP falhar)
- \`LIGHTHOUSE-RESULTS.md\` — template para owner preencher
- 3 cenários de veredito pré-formulados (passa / regressão isolada /
  regressão ampla)

Owner executa em ambiente production-like real e registra resultado.
Sem hipótese sem dado.

### Sem smoke probe de performance preemptivo (D5)

ADR-019 — sem gargalo concreto observado, smoke probe é especulativo.
Lighthouse CI custaria 30-60s por PR + risco de false positives.
Aguarda evidência de regressão real para criar.

### Wave 4 tag final = `v0.4-final-public` (não `v0.4.6-polish`)

Decisão D2(b) da Sprint 4.6. Comunica "Wave 4 público concluído"
melhor que "polish da sub-sprint 4.6". 4.5 fica como carryover claro
para Wave 5.
