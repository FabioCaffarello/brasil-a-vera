# Release `v0.10.0-area-logada`

> Wave 10 — Área logada — fechamento
> Tag publicada em: 2026-05-19
> Sucessor de: [`v0.9.0-votacao-360`](https://github.com/FabioCaffarello/brasil-a-vera/releases/tag/v0.9.0-votacao-360)
> Próximo: Wave 11 sem cronograma fixo

## Resumo executivo

A Wave 10 funda a **área autenticada** do produto (`/painel/*`) sem
deslocar o cidadão anônimo do centro da plataforma. Login é opt-in;
todas as features de leitura do site continuam funcionando sem conta.
A nova proposta de valor para quem opta por entrar é simples:
acompanhe parlamentares e receba um resumo semanal por email
**sem precisar garimpar** — o cidadão delega ao produto a leitura
sistemática que ele faria à mão se tivesse tempo.

Sob a UX modesta, a Wave 10 entrega muita arquitetura:

- **Autenticação completa** via Clerk, com custom sign-in/up no
  domínio próprio (sem Account Portal) e middleware `auth.protect()`.
- **5 tabelas novas** no schema `usuario` — `user_profile`, `follows`,
  `alert_policy`, `consent_log`, `alert_delivery`, `data_request` —
  e zero migrations destrutivas (apenas CREATE TABLE incremental).
- **Sistema de alertas semanais** via Resend, com idempotency key
  SHA-256 unique por (`user_id` + `period` + `cadence` + `channel`),
  agregadores puros testáveis (votação/gastos/proposições/divergências)
  e composer de markdown server-side.
- **Framework LGPD completo** — `/privacidade` SSG versionada,
  `ConsentGate` modal de re-aceite em bump de versão, endpoints
  export/erase/anonimizar, dashboard `/painel/configuracoes/meus-dados`,
  cron diário de lembrete (25-29d) + hard-delete (30d), reativação
  automática via login.
- **3 ADRs publicados** (029, 030, 031) cobrindo modelo de dados +
  topologia de auth, sistema de alertas + Resend, framework LGPD.

26 PRs entregues. Wave 10 fecha o ciclo "cidadão pode ler tudo
anonimamente" → "cidadão pode delegar acompanhamento ao produto", sem
quebrar a primeira parte.

## Achados-chave (Wave 10)

### Múltiplos `<ClerkProvider>` em árvores siblings = SDK quebra

Bug descoberto **só depois do deploy em produção** após Etapa 1. Bem
em vez de em testes locais. O plano original do ADR-022 §4 escolheu
"Opção B" (Provider escopado em `auth-island.tsx`, lazy) para evitar
+50kb gzip em rotas anônimas. O ADR-029 §6 escolheu "Opção C"
(Provider em route group `(authenticated)/`). Quando ambos
coexistiram, Clerk acusou:

```
@clerk/nextjs: You've added multiple <ClerkProvider> components
```

**Resolução**: Provider único no root layout (`src/app/layout.tsx`).
Aceita o custo de +50kb gzip em rotas anônimas em troca de auth
funcional em rotas privadas. **Princípio 13 do CLAUDE.md** (validação
empírica) entra em ação: hipóteses sobre comportamento de SDK não
substituem deploy real. Addendum no ADR-029 §6 v2 documenta a revisão.

### Etapa 8 deferida — primeira aplicação prática do ADR-019 em Wave 10

A Etapa 8 (modulação `alert_period` para período eleitoral) era item
de plano originalmente aceito. Próximo do início, owner pediu deferral:
"sem evidência empírica de que cadência semanal é insuficiente em
período eleitoral; reabrir se telemetria pós-launch sinalizar gap".
Decisão registrada em PR #324 com riscado dos itens dependentes em
LOGGED-AREA-VISION (§6 decisão de modulação, §8 plano, §9 risco
neutralizado, §10 cap mitigation neutralizado, §11 reentrada). Esse
foi o jeito mais limpo até agora de aplicar ADR-019 na prática: cortar
escopo planejado quando o gargalo não materializou.

### Idempotency key por canal — divergência da VISION §6

LOGGED-AREA-VISION §6 definiu `idempotency_key = sha256(user_id +
period_start + cadence)` (três componentes). A Etapa 7.1
**divergiu conscientemente** para incluir `channel` como quarto
componente — sem isso, um usuário com `channel_email=true` E
`channel_inapp=true` tentaria inserir duas linhas com a mesma key
unique e a segunda batia conflito, fazendo o segundo canal sumir
silenciosamente. Decisão documentada no comment do `schema.ts` e nos
testes de `cron-period.test.ts`.

### Reativação via login, não rota dedicada

A LOGGED-AREA-VISION mencionava "reativação" sem especificar fluxo.
Na Etapa 9.6, optou-se pelo caminho mais simples: o lazy upsert do
`/painel` (`upsertUserProfileFromClerk`) limpa `deleted_at = NULL`
no ON CONFLICT. **Login É a reativação** — sem rota
`/api/painel/reativar`, sem botão "voltar". O CTA do email de
lembrete enviado entre 25-29d aponta direto para `/sign-in`. Custo
mínimo, comportamento intuitivo.

### `localStorage` defensivo — hedge consciente sem hit em produção

PR 9.7 entrega modal `<MigracaoLocalStorageModal>` que detecta a
chave `bav.parlamentares.favoritos` e oferece importar para `follows`.
Grep do codebase confirma: **nenhuma versão do produto jamais gravou
nessa chave**. O componente é defensivo para versões hipotéticas em
browsers de usuários que aterrissaram em feature branches antigos. Em
produção real é no-op. VISION §9 já antecipava o concern: "hedge
barato; remover na Wave 11 se confirmado zero hits em telemetria".

### jsdom no Node 22+ não fornece `localStorage` funcional

Edge case técnico encontrado durante os testes da Etapa 9.7. jsdom
retorna um objeto `{}` com `null prototype` no lugar do Storage
nativo. Solução: shim `MemoryStorage` no test file via
`Object.defineProperty(window, 'localStorage', { value: ... })`.
Isolado ao test; nenhum impacto em produção.

### Salt de IP fixo (não rotativo) — trade-off LGPD consciente

A política de privacidade declara que armazenamos hash do IP no
momento do consentimento, não o IP em claro. Implementação Wave 10:
`SHA-256(ip + ":" + YYYY-MM-DD + ":" + salt_fixo)`. O salt vem de
`IP_HASH_SALT` Workers Secret (32 bytes hex). Trade-off declarado:
salt fixo simplifica operação mas, em caso de vazamento do salt,
adversário com dump do banco pode enumerar IPs (4 bilhões IPv4 é
tratável). Salt rotativo diariamente seria mais defensivo mas com
custo operacional maior. Decisão Wave 10: aceitar salt fixo;
reabrir como rotativo se ANPD entender que é exigência. Documentado
em [LOGGED-AREA-VISION §9](../product/LOGGED-AREA-VISION.md#9-riscos-e-questões-abertas)
como questão aberta.

## Divergências do plano original

| Item planejado | Decisão real | Justificativa |
|---|---|---|
| **Etapa 8** modulação `alert_period` | Deferida para Wave 11+ | Sem evidência empírica; ADR-019 |
| **Rate limit follows via Workers KV** (Etapa 10) | Skip; cap 200 já protege | Volume Wave 10 (≤750 MAU) não justifica infra KV nova |
| **Smoke E2E signup→follow→alerta** (Etapa 10) | Skip | Clerk signup automatizado exige bot account; deferir até 1k+ MAU |
| **R2 signed URL para export** (Etapa 9.4) | JSON inline no response | Volume Wave 10 não justifica binding R2; payload <250 rows por usuário |
| **Workers Queue para processar `data_request`** (Etapa 9.4) | Síncrono no request handler | Volume baixo; ADR-019 |
| **Idempotency key** sha256(user + period + cadence) (VISION §6) | + `channel` como 4º componente | Bug encontrado em design; suporta 1 row por canal |
| **`ClerkProvider`** escopado (ADR-022 B + ADR-029 C) | Único no root layout | Múltiplos Providers quebram Clerk em runtime |

## O que entra na Wave 11

Sem cronograma fixo. Candidatos abertos:

- Reabrir modulação `alert_period` se telemetria pós-launch indicar
  necessidade.
- Rate limit follows via Workers KV se telemetria mostrar abuso.
- Smoke E2E quando bot account Clerk valer o esforço (≥1k MAU).
- R2 para export se payloads ultrapassarem alguns MB (improvável
  enquanto volumes forem como hoje).
- Async processing de `data_request` se sync atingir timeout Worker
  (50ms CPU padrão).
- Rotação diária do salt de IP se ANPD entender que é exigência.
