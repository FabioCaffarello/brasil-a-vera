# Release `v0.9.0-votacao-360`

> Wave 9 — Votação 360° — fechamento
> Tag publicada em: 2026-05-19
> Sucessor de: [`v0.8.0-proposicao-360`](https://github.com/FabioCaffarello/brasil-a-vera/releases/tag/v0.8.0-proposicao-360)
> Próximo: Wave 10 sem cronograma fixo

## Resumo executivo

A Wave 9 fecha o triângulo `Parlamentar × Proposição × Votação`,
estendendo ao eixo "evento legislativo" (`/votacoes`) o padrão
arquitetural consolidado em Waves 7 e 8 (perfil 360°: cursor pagination,
KpiStrip + Accordion mobile + Compartilhar, cache de edge nas queries,
Recharts dynamic-imported). Mas votação não é só mais uma rota a portar:
parlamentar é entidade contínua, proposição é processo, votação é
**evento instantâneo com tensão dramática única** — orientação de
bancada × voto individual, disciplina × rebelião, margem de decisão. A
Wave 9 captura essa singularidade.

Entrega ancorada em **plano cravado com 8 decisões (D1-D8)** antes do
primeiro PR de execução abrir. Decisões críticas: D1 KpiStrip híbrido
(SIM · NÃO · Margem · Disciplina), D3 hemiciclo desktop + Donut mobile,
D5 seções Disciplina + Rebeldes condicionais, D7 client component filter
+ SSG. **A parte SSG do D7 foi revertida em runtime** após primeiro
deploy revelar incompatibilidade do OpenNext Workers com `generateStaticParams`
sem binding R2 — lição empírica forte que vira memória operacional
(`feedback_ssg_workers_r2.md`) e revisão da D7 no plano.

Decisão transversal não-óbvia da rodada de cravamento: **1 tag final
por wave inteira**, sem tags intermediárias `-alpha.X` ou `-rc.X` por
sprint (memória `feedback_release_cadence.md`). Padrão observado em
Waves 7 e 8 → v0.7.0 e v0.8.0, sem variantes. Reforça que a wave é
unidade narrativa única, não série de incrementos.

24 PRs entregues + 1 fix de runtime no meio do caminho. Wave 9 fecha o
redesign de `/votacoes` no mesmo nível arquitetural das Waves 7 e 8
**e introduz a primeira feature de identidade narrativa única**
(Disciplina partidária + Rebeldes) — só faz sentido em votação, não
porta de parlamentar nem de proposição.

## Achados-chave (Wave 9)

### Sintaxe `hsl(var())` aninhada com tokens OKLCH-completos → fills pretos

Bug histórico em **todos os charts SVG/Recharts** (Wave 7 + 8 + 9) descoberto via screenshot do owner pós-Sprint 9.4. Tokens em `globals.css` são OKLCH-completos (`oklch(0.6 0.13 240)`), mas consumers usavam:

```tsx
fill="hsl(var(--chart-1))"  // expande para hsl(oklch(...)) — INVÁLIDO → fill #000
```

A sintaxe `hsl(var(--X))` exige token em componentes HSL crus (`220 60% 50%`), padrão pre-Tailwind-v4. Esse projeto migrou para OKLCH no Sprint 4.0 (Wave 4) mas os charts (Wave 7 em diante) herdaram a sintaxe antiga sem revalidação visual. Charts ficaram com fills pretos invisíveis em light theme; em dark theme alguns davam impressão de funcionar por contraste fortuito com fundo escuro.

Fix #304 (Sprint 9.5 PR6) corrigiu 30 ocorrências em 7 arquivos:
- `fill="hsl(var(--X))"` → `fill="var(--X)"`
- `bg-[hsl(var(--X))]` → `bg-[var(--X)]`
- `hsl(var(--X) / N)` → `color-mix(in oklch, var(--X) N%, transparent)` (CSS Color Module Level 5)

Mesmo PR aplicou regra de dataviz "ranking → uma cor (`--chart-1`) + opacidade decrescente `[1, 0.85, 0.7, 0.6, 0.5, 0.4, 0.3]`" em 3 charts (gastos, apoio por partido, disciplina). Documentado em DESIGN-TOKENS.md §"Padrões de uso em charts".

Lição empírica acompanhada: meu PR #303 anterior (color fix Okabe-Ito) mudou o valor do token confiante de que resolveria "barras pretas", mas o consumer nunca conseguia parsear o token. Mudar OKLCH 0.32 → 0.6 não muda nada quando o wrapper `hsl()` invalida a expressão inteira. Memória `feedback_visual_empirical_validation.md` salva: mudanças visuais exigem screenshot ou WCAG empírico antes de mergear; Biome + TS + build não basta.

Trade-off WCAG documentado: cap 0.3 de opacidade em light theme produz contraste ~1.3:1 contra background, abaixo do WCAG 1.4.11 (3:1). Estado anterior era ~1:1 (preto puro) — fix é melhoria significativa mesmo no extremo do ranking. Dark theme funciona melhor (2.5:1 no cap). Issue aberta para reavaliação se light theme deixar de ser dormente.

### OpenNext em Workers sem R2 → `generateStaticParams` quebra em runtime

PR 9.2.1 (#286) introduziu `generateStaticParams` top-200 em
`/votacoes/[id]`, confiante de que o "ISR fallback nativo do Next 16"
cobriria long-tail. Pós-deploy, **todas as URLs de detalhe retornaram
HTTP 500** em produção. Causa: OpenNext exige binding R2 explícito
como incremental cache para servir páginas SSG/ISR — sem R2, qualquer
rota com `generateStaticParams` quebra em runtime com erro genérico
("Internal Server Error" no body, sem stack trace útil).

A limitação **já estava cravada** no comentário do `wrangler.jsonc`
("todas as rotas são dinâmicas (ƒ). Revisitar quando entrar
ISR/Cache Components") e na Issue #58. Não foi conectada no plano.

Fix #293 reverteu o `generateStaticParams`, mantendo a parte boa do
PR 9.2.1 (client-side filter em `VotosIndividuais` via
`useSearchParams`). Performance preservada pelo cache de edge nas
queries (`cached()` wrappers do Sprint 9.0 PR 9.0.3, TTL
`votacaoHistorica` = 7d). Paridade restaurada com `/parlamentares/[id]`
e `/proposicoes/[tipo]/[numero]/[ano]` (também dinâmicas).

Lição registrada em `feedback_ssg_workers_r2.md` (memória operacional)
+ D7 revisada no `WAVE-9-VOTACOES-PLAN.md`. Critério futuro: validar
SSG/ISR em produção via `curl` empírico **antes** de mergear, conforme
CLAUDE.md §13.

### Hemiciclo SVG sem libs externas escala a 513 pontos

Sprint 9.3 PR4 (#295) implementou um parliament chart semicircular puro
em SVG, sem Recharts, sem libs externas — ~120 linhas (algoritmo + JSX).
Algoritmo:

1. Calcula fileiras concêntricas iterando `INNER_R=80` → `OUTER_R=280`
2. Capacidade por fileira = `perímetro / espaçamento` (14 unidades)
3. Distribui votos proporcionalmente, ajustando arredondamento
4. Posiciona cada ponto via `cos/sin` do ângulo (π → 0, esquerda →
   direita)

**Cardinalidade testada:** Câmara (513 pontos) cabe em 8-10 fileiras.
Senado (81) em 4-5. Comissão pequena (15) em 2-3.

Server Component, zero JS no cliente. Tooltip nativo via `<title>`
SVG element — screen readers leem naturalmente. `hidden md:block` no
caller; mobile (<768px) mantém Donut consolidado porque pontos
individuais ficariam ilegíveis em 375px.

Trade-off aceito v1: ordena por tipo de voto (SIM → centro → NÃO),
sem cluster por partido. Cluster por partido enriqueceria a leitura
("vejo bancada do PT toda em vermelho aqui") mas adiciona complexidade
de algoritmo; reabrir em wave futura se houver demanda.

### Disciplina + Rebeldes pareadas como identidade narrativa única

Wave 9 introduz duas seções condicionais que **só fazem sentido em
votação**: `DisciplinaPartidariaChart` (% de cada bancada que seguiu
orientação) e `RebeldesList` (nomes que votaram contra orientação).
Pareadas: aparecem/somem juntas via `disciplinas.length > 0`. Quando
votação não tem orientações de bancada registradas, ambas as seções
somem (sem placeholders vazios, sem inventar narrativa onde dado não
suporta — P2).

Caso especial cravado: votação **com** orientações + zero rebeldes
renderiza empty state **positivo** ("Disciplina total entre as
bancadas com orientação"). Não é ausência de dado, é informação
política — tem que aparecer.

Semântica isolada em funções puras em
`src/modules/votacoes/domain/disciplina.ts` (17 testes Vitest, Sprint
9.0 PR 9.0.2):
- **Voto ativo**: SIM, NAO, OBSTRUCAO (AUSENTE/ABSTENCAO não)
- **Orientação efetiva**: SIM, NAO, OBSTRUCAO (LIBERADO não)
- **Rebelde**: orientação efetiva ∧ voto ativo ∧ `voto ≠ orientação`
- **Disciplina**: `seguiram / totalAtivo * 100`, denominador exclui
  ausências/abstenções

### Margem como eixo narrativo central, reforçada em 4 lugares

D1 do plano cravou "Margem" como um dos 4 slots do KpiStrip (não
"Abstenção" como seria portagem direta de tipos de voto). A decisão
reverberou em 4 lugares na wave:

1. **KpiStrip slot 3** (Sprint 9.2 PR4): `+N` + hint "votos a favor"
   ou "votos contra"
2. **CompartilharButton WhatsApp/X** (Sprint 9.2 PR3): templates
   incluem "Aprovada por X a Y (Câmara)" — destaca margem em vez de
   tally puro
3. **MargemDecisaoBar CSS** (Sprint 9.3 PR3): barra bilateral SIM↔NÃO
   com width proporcional + label central da margem
4. **OG image v2** (Sprint 9.5 PR1): mesma barra bilateral renderizada
   via flex/width % em Satori — preview de share mostra margem em <1s

Reforça **P9 do plano** (princípio novo da Wave 9: "votação é evento"
— o instante decisivo tem 2 lados, não 5 categorias).

### Cores semânticas consistentes cross-chart no domínio

5 visualizações diferentes na Wave 9 usam o mesmo mapeamento
semântico:

| Categoria | CSS var | Usado em |
|---|---|---|
| SIM | `--success` | Donut consolidado, Bar por partido, MargemDecisaoBar, Hemiciclo, Disciplina chart |
| NÃO | `--destructive` | Donut, Bar, MargemDecisaoBar, Hemiciclo |
| Abstenção | `--foreground-muted` | Donut, Bar, Hemiciclo |
| Ausentes | `--warning` | Donut, Bar, Hemiciclo |
| Obstrução | `--foreground-subtle` | Bar (segmento empilhado), Hemiciclo |

Usuário não reprocessa o que cada cor significa entre charts no mesmo
detalhe. Justificado como **sinal** (decisão de voto), não escolha
estética — P4 do plano (reserva `--accent` para inflexão narrativa)
permanece intacto.

## Decisões registradas durante a Wave

### 1 tag final por wave (sem `-alpha.X` ou `-rc.X` por sprint)

Cravada na rodada de planejamento. Owner enxerga cada wave como
unidade narrativa única ("Parlamentar 360", "Proposição 360", "Votação
360"); tags intermediárias diluem a entrega e quebram a estética dos
release notes consolidados. Padrão observado em Waves 7 e 8 → v0.7.0 e
v0.8.0.

Salvo em `feedback_release_cadence.md` para futuras waves.

### Page-size 24 (vs 20 do ADR-026) na listagem de votações

ADR-028 §1 cravou page-size 24 (não 20 herdado do ADR-026) com
justificativa de divisibilidade harmônica:

- 24 é divisível por 2, 3, 4, 6 → preenche grids harmonicamente em
  qualquer breakpoint (mobile 1×24, tablet 2×12, desktop 3×8, wide
  4×6)
- 20 não é divisível por 3 nem 4 → gera grids irregulares
- Card de votação é mais denso (3-4 linhas) que parlamentar/proposição
  (5+), absorve 24 sem rolar excessivamente

Demais propriedades do cursor (token opaco versionado v1, helpers,
"Mostrar mais", redirect 308 em versão desconhecida) **idênticas ao
ADR-026**.

### D7 revisada após fix #293: dinâmica + cache de edge ≠ SSG

D7 original cravou "client component filter + SSG + ISR". Após fix
#293, foi revisada para "client component filter + página dinâmica +
cache de edge nas queries". A parte client filter (`useSearchParams`
em `VotosIndividuais` + filter in-memory) **permanece** — não causa
nenhum problema, página agora é dinâmica anyway. SSG fica para quando
Issue #58 entregar R2 incremental cache, momento em que as 3 rotas
(parlamentar/proposição/votação) podem ganhar SSG simultaneamente.

### Hemiciclo desktop + Donut mobile via `hidden md:block` (não container query)

Plano original D3 mencionou container query. Em prática, `hidden md:block`
/ `md:hidden` no caller é mais simples, estável e segue padrão do
Accordion mobile (Sprint 9.2 PR5). Container query teria valor se o
widget aparecesse em containers de tamanhos variados, mas aqui é
sempre o SectionCard de mesma largura.

### `?offset=` aceito por 1 release (ADR-028 §4), depois removido

Compat de deep-links externos. Durante Sprint 9.1, rota `/votacoes`
aceita ambos:

- `?offset=N` (deprecated) — `permanentRedirect(308)` strip do param,
  preservando filtros e cursor
- `?cursor=<token>` — novo padrão, versionado v1

Após `v0.9.0-votacao-360` shipar, handler `?offset` pode ser removido
em wave seguinte. Janela de 1 release preserva links externos
compartilhados em estado-estável.

### Reutilização agressiva de queries cacheadas no detalhe

`getDisciplinaPartidariaPorVotacao` é chamada **uma vez** no Promise.all
da page.tsx e reusada em 4 consumers: KpiStrip slot Disciplina (PR
9.2.4), `DisciplinaPartidariaChart` (PR 9.4.1), condicional do
`RebeldesList` (PR 9.4.2), condicional do SectionNav/Accordion items.

Mesmo padrão para `getRebeldesByVotacao` (1 chamada → 2 consumers) e
`getVotacoesRelacionadas` (1 chamada → 1 consumer mas cached 7d para
revisita).

Resultado: cache hit das queries detalhe cobre revisita inteira sem
nova ida ao Neon. CLAUDE.md §12 (scale-to-zero) respeitado.
